# Spotter — reviewer setup and evidence

## A. Fastest path: self-discovering public verification (no wallet)

1. Open https://bearbaba.github.io/spotter/ — do not connect a wallet.
2. Wait for **Explore verifications** to read the existing contract's finalized Jobs automatically. Check visible newest-first Job cards, IDs, owner and OPEN/SUBMITTED/HIT/MISS/DEAD status. Refresh and Load more are read-only.
3. Choose **Read proof** on any Job. Confirm that it displays the live contract's status, original claim, public URL (when submitted), reason and SHA-256 (when evaluated).
4. Optionally use the historical Sample verification Job #1. Review may be completed without knowing any Job ID or Studio hash beforehand.
5. Independently cross-check a shown Job's ID using the Studio contract `get_job` view on the same Studionet address.

**Wallet continuation from existing contract state:** Connect a wallet (wallet permission but no blockchain transaction), choose **My jobs** for your own activity or **All jobs** to participate permissionlessly. On an OPEN Job select **Submit a source**; on a SUBMITTED Job select **Run verification**. The interface rereads the finalized Job and loads the question/rubric without a new `open_job`. Anyone may judge according to the deployed contract, but only the first hunter may replace an already-SUBMITTED URL. Check any write carefully in MetaMask.

**Known already-finalized transactions:** `0xaa6cead7f9e18e900c1d74a91c4adfc54019dadb2299c4a6f1619d8aca0bbe06` returned OPEN Job #5 and `0x2c998a84010127893291b9819e19105d94c65077d394ba0e4a1dab3d158d8bdd` returned OPEN Job #6 when inspected. These are transaction outcomes; they are not completed HIT/MISS/DEAD verdicts. Browsing these jobs requires no hash paste.

## B. Dependency-free local build and tests

```bash
git clone https://github.com/bearbaba/spotter.git
cd spotter
npm run verify
python3 -m http.server 8080
```

Requirements: Node 20+, Python 3. Open http://localhost:8080 and follow Path A. No `npm install` step, API key, wallet, or seed phrase is needed for offline tests and read-only use. The `dist/` directory generated by `npm run build` is a static copy of the site.

## C. Full wallet smoke test (optional; real signed **Studionet** writes)

1. Use a test wallet with Studionet chain ID `61999` (`0xf22f`), RPC `https://studio.genlayer.com/api`. Do not use mainnet.
2. Connect MetaMask and confirm chain 61999.
3. **Prefer an already-open job**: select any eligible OPEN Job in **All jobs / My jobs → Submit a source** (read-only selection). Only create a new job if you specifically intend a new claim and no reusable Job exists. If creating, choose **HIT example → 1 · Create job** and approve the explicit wallet prompt.
4. The interface should fill the Job ID using the receipt return, or verify a matching new `last_job_of` value against pre-write ID, wallet, question and rubric. If this cannot be matched, check Studio and paste the exact ID manually.
5. Click **2 · Submit evidence**. After finalization confirm status `SUBMITTED`.
6. Click **3 · Run verification**. After finalization click **Read proof** and inspect `status`, `page_hash`, `page_chars`, `fetch_ok`, `fail_kind` and `justification`. Fresh HIT/MISS/DEAD is not predetermined; compare against actual fetched evidence.
7. If waiting times out **do not click the same write again**. Open **Transaction details & troubleshooting** and click **Resume previous transaction** (read-only). MetaMask initially provides an EVM hash. If a mined `NewTransaction` event is present, the distinct GenLayer transaction ID appears with an Explorer link. When the event is missing, the app checks the actual finalized contract state for a strict match; if unverified it remains pending. For legacy records lacking a pre-write baseline, manually inspect chain state before using **Clear local tracking**, which never cancels an on-chain transaction.

If contract deployment source, public URL, test GEN or RPC is not accessible, note the limitation instead of asserting a passing live smoke test.

## D. Diagnose an existing unresolved wallet transaction (read-only)

**Never send the same action again merely because the UI is waiting.**

1. Open **Transaction details & troubleshooting** on the same browser tab that saved the pending transaction.
2. Choose **Inspect transaction (read-only)**. This performs only RPC reads (`eth_chainId`, `eth_getTransactionByHash`, `eth_getTransactionReceipt`, and contract views). It does not request a signature, change chain settings, or submit a transaction.
3. Inspect the actual wallet transaction destination against the expected Studionet consensus address `0xb7278A61aa25c888815aFC32Ad3cC52fF24fE575`, receipt status, event count and latest finalized Job ID. A mined EVM transaction does not alone prove the GenLayer action was accepted.
   - If the receipt includes logs but no recognized `NewTransaction` event, the inspector shows each log's public emitter address and `topic[0]` rather than pretending there were no logs.
   - The inspector separately reads historical **Job #1** from the deployed Spotter contract to distinguish a missing Studio editor entry from absent final on-chain data. An unavailable or empty read does not alone prove the contract was deleted.
4. Use **Copy full tx hash** to send the complete hash for diagnosis (public transaction ID; **never provide a seed phrase, private key or signing request**). If the clipboard is unavailable, the page displays the full hash for manual copying.
5. Leave the previous write tracked while its status is unknown. **Clear local tracking** does not cancel the transaction and should be used only after inspecting the chain state.

If an older browser tab was closed, find the full transaction hash in MetaMask Activity. The on-page diagnostic cannot recover unsaved data from a different browser session.

## Security/interpretation notes

- The frontend uses **genlayer-js v0.18.10**, whose `writeContract` estimates EVM gas internally. It does not expose the newer `estimateTransactionFeesForWrite` or `waitForFinalization` helpers. The frontend does not automatically sign or retry writes. Job browsing, selection and public proof reading require no wallet signature.
- Read-only views work without wallet authentication.
- Job ID is obtained from the return when available, otherwise a cautious same-wallet `last_job_of` read compared with the recorded pre-write baseline and exact claim. Identical concurrent same-wallet jobs cannot be proven unique without the original receipt; use Studio for final attribution.
- `judge` is not restricted to a single authority in the existing contract. Anyone able to call it can request evaluation of a submitted job.
- The first hunter's URL stays locked while SUBMITTED; there is no monetary reward path.
- `PARSE` is a nonterminal error state and should not be described as a fourth successful verdict.
- The displayed page hash is a validator-observed text digest, not a cryptographically authenticated snapshot of the entire website.


### Case-sensitive sender lookup on the existing deployed contract

`last_job_of(who: str)` uses an exact string key stored by `str(gl.message.sender_address)`. If MetaMask returns a lowercase address but Studio shows a checksum-cased `poster`, a direct `last_job_of(lowercase)` call can return an empty string even after an accepted `open_job`. The frontend first checks the wallet address and then reads up to 16 finalized sequential Job records to find the exact `poster` string for the same address, retries `last_job_of`, and verifies the returned Job against its original action. This is read-only; **do not resend the prior transaction**.

If there are multiple identical claims from the same wallet, use Studio to inspect each transaction's execution return and establish the exact ID. Do not assume a state-only match uniquely ties a specific EVM hash to a Job.

### Inspect an exact GenLayer transaction hash

The saved wallet hash may itself be indexed as a GenLayer transaction in Studio Explorer. The frontend now attempts `getTransaction({hash})` **first** and reports the direct GenLayer result in read-only diagnostics. A successful `FINALIZED / SUCCESS` response verifies the transaction status but not its automatically inferred Job ID; locate **GenVM Execution → Return Value** in Studio Explorer for a definitive ID. EVM `NewTransaction` logs are only a fallback and may be absent even if Studio confirms an accepted transaction.

### Continue a recovered Job (Studio-confirmed IDs)

If an existing `open_job` transaction is FINALIZED and the `Return Value` explicitly identifies Job #5 or Job #6, use **Recover transaction by hash → Inspect transaction hash** to read it in any tab. After connecting a Studionet wallet, select **Continue with Job #N**. The page rechecks the actual finalized Job ID and status, fills its question and rubric, and enables only the appropriate separately approved write (**Submit evidence** for OPEN or **Run verification** for SUBMITTED, which is permissionless under the deployed contract).

**Do not click Create job.** Recovery and Continue themselves are read-only and should not display a MetaMask signing prompt. Only subsequent separate user-approved Submit/Judge actions send writes. If the original wallet does not match the Job poster or a previous transaction is still pending in this tab, no write step is enabled.
